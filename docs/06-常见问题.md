# 06 常见问题（排障手册）

本文按“看到的症状”组织，每条都写 **现象 / 原因 / 解决**。

- 命令里的 `ad` 与 [03-工作流SOP](03-工作流SOP.md) 相同：Windows 是 `.\aidrama.bat`，Linux 是 `./aidrama.sh`，也可以写 `python -m aidrama`。
- `<stack>` 指安装目录：Linux 默认 `~/aidrama-stack`；Windows 默认 `D:\aidrama-stack`，没有 D 盘时是 `%USERPROFILE%\aidrama-stack`。
- 引用的 ComfyUI issue / PR 编号来自 [research/09-ComfyUI与5090调优](research/09-ComfyUI与5090调优.md)，H3 的 issue 编号来自 [research/07-运镜与动作控制](research/07-运镜与动作控制.md)。
- 本流水线在没有 GPU 的云端开发，Windows 安装脚本只做过语法检查。标“未确认”的做法没有在 5090 上实测。

## 0. 排障前先做三件事

1. **跑体检**：`ad doctor`。它依次检查：ffmpeg/ffprobe 是否在 PATH；ComfyUI 版本是否 ≥ 0.38、显卡和显存、18 个必需原生节点、`configs/models.yaml` 里各模型组的文件；配置里三个音频地址的 `/health`（配音 9001，音色设计和识别/对齐默认都是 9002）；LLM 接口和模型名；H3 官方提示词指南是否已下载。ffmpeg、ComfyUI 版本与节点、`core` 模型组、音频服务、LLM 中任何一项打叉，结论都会是“有必需项未就绪”；其他模型组和提示词指南缺失只提示、不算失败。
2. **看日志**：见第 12 节。
3. **区分是环境问题还是工程问题**：`ad init-demo projects/demo` 后运行 `ad run projects/demo ep01 --mock`。mock 模式不连接任何模型，用占位素材跑完全流程。mock 能过而真实运行失败，问题在服务或模型；mock 也失败，问题在工程文件或 aidrama 本身。也可以在仓库 `.venv` 里跑 `python -m pytest -q tests`（不需要 GPU）。

## 1. 显卡驱动与 CUDA

### 1.1 驱动低于 580，或 `torch.cuda.is_available()` 为 False

- **现象**：安装脚本第 0 步提示“驱动 … < 580”；第 2 步打印 `available False`；ComfyUI 跑在 CPU 上，极慢。
- **原因**：PyTorch cu130 和 comfy-kitchen 的 CUDA 预编译包都要求 r580 及以上驱动。
- **解决**：Windows 到 nvidia.cn 装最新的 Game Ready 或 Studio 驱动；Linux 执行 `sudo ubuntu-drivers install` 或 `sudo apt install nvidia-driver-580-open`，然后重启。用 ComfyUI 自己的 Python 验证：

```bash
<stack>/ComfyUI/.venv/bin/python -c "import torch;print(torch.__version__, torch.version.cuda, torch.cuda.is_available(), torch.cuda.get_device_capability())"
# Windows：<stack>\ComfyUI\.venv\Scripts\python.exe -c "..."
# 期望：版本带 +cu130，CUDA 13.0，True，(12, 0)
```

### 1.2 Linux 提示“当前不是 open 内核模块驱动”

- **现象**：`install.sh` 输出“RTX 50 系需要 nvidia-driver-xxx-open”；或者驱动装了，但 `nvidia-smi` 找不到显卡。
- **原因**：Blackwell 架构（RTX 50 系）只能用 NVIDIA 的 open 内核模块。脚本通过 `/proc/driver/nvidia/version` 里有没有 “open” 字样（不区分大小写）来判断。
- **解决**：卸掉闭源版，安装 `nvidia-driver-580-open`（或更新的 `-open` 版本）。开着 Secure Boot 的机器可能还要按安装提示登记 MOK 密钥，否则内核模块加载不了（通用 Linux 经验，未确认）。

### 1.3 Windows 报 `Torch not compiled with CUDA enabled`

- **原因**：从 PyPI 装到了 CPU 版 torch。PyPI 上的 Windows 版 torch 没有 CUDA。
- **解决**：从 cu130 索引重装：`uv pip install --python <stack>\ComfyUI\.venv\Scripts\python.exe torch torchvision torchaudio --index-url https://download.pytorch.org/whl/cu130 --reinstall`。

### 1.4 int8 模型特别慢，或 nvfp4 文本编码器占了约 28GB

- **原因**：torch 不是 cu13x 时，comfy-kitchen 的 CUDA 后端加载不了，nvfp4 被上转成 fp16，int8 走慢速路径（ComfyUI #11864）。
- **解决**：按 1.1 的命令确认 `torch.version.cuda` 是 13.0，不是的话按 1.3 重装。不要在 ComfyUI 环境里装其他项目要求的 cu12x torch。

## 2. Python 包安装（uv / pip / 镜像）

### 2.1 pip 下载慢、超时

- **解决**：安装时加 `-PipMirror tuna`（Windows）或 `--pip-mirror tuna`（Linux），也可以用 `aliyun`。脚本通过 `UV_DEFAULT_INDEX` 让 uv 使用镜像。网络不稳时可以再加大 uv 的超时：`UV_HTTP_TIMEOUT=300`。
- 镜像同步有延迟：如果报某个固定版本的包找不到（例如 ComfyUI requirements 里锁定的 `comfy-kitchen`、`comfy-aimdo`），临时去掉镜像参数重跑这一步即可。安装脚本可以重复运行，已完成的步骤会跳过。

### 2.2 PyTorch 下载慢

- **原因**：PyTorch 必须从 `download.pytorch.org/whl/cu130`（Qwen 音频环境用 `cu128`）下载，PyPI 镜像对 Windows 没用。
- **解决**：给这一步挂代理；或者在网络好的地方先下好 wheel 文件，再 `uv pip install --python <环境的 python> <wheel 文件>`。
- Linux 例外：调研笔记记录 PyPI 上 Linux 版 torch 2.14.1 本身就是 cu130 构建（自带 CUDA 13.0.3），可以从 PyPI 镜像安装；装完务必用 1.1 的命令确认 `torch.version.cuda` 是 13.0。

### 2.3 Windows：winget 装完 git/ffmpeg/uv 后仍提示找不到命令

- **解决**：脚本会提示“请关闭并重新打开 PowerShell 后再运行本脚本”，照做即可。没有 winget 的系统，请手动安装 Git、FFmpeg、uv 并加入 PATH。
- 另外两条经验做法：开启长路径支持（`LongPathsEnabled=1`，并执行 `git config --system core.longpaths true`），安装到短的纯英文路径；给 `<stack>` 目录加 Windows Defender 排除项，避免每次加载 20GB 级的 safetensors 都被扫描。

## 3. 模型下载（HuggingFace 打不开）

### 3.1 HuggingFace 不通，下载卡住或报错

- **解决**：安装时加 `-Source modelscope`（Linux `--source modelscope`），或 `hf-mirror`。之后单独补模型：

```bash
python scripts/download_models.py --comfy <stack>/ComfyUI --groups core,fast --source modelscope
python scripts/download_models.py --groups all --list      # 只看清单和体积
```

- `download_models.py` 会把 `huggingface.co` 地址改写成 hf-mirror 或 ModelScope 地址，按 `--source` 指定的顺序逐个尝试：`auto` 为 HuggingFace → hf-mirror → ModelScope；`modelscope` 为 ModelScope → hf-mirror → HuggingFace。
- 部分仓库（FastH3、lightx2v 的 Turbo LoRA 等）在 ModelScope 上有没有镜像未确认，脚本会自动回退到下一个来源。

### 3.2 下载报“下载中断”“文件大小不对”“返回的是 …”或 HTTP 401/403/404

- **下载中断（已下/总大小），重跑会自动续传**：连接断了。临时文件 `<文件名>.<来源主机>.part` 会保留，脚本在本次运行里会对同一来源再试几次；重跑同一条命令也会从断点继续。续传只在同一个来源内进行。
- **文件大小不对 / 服务器报告的大小只有 …**：拿到的文件和 `configs/models.yaml` 里的体积对不上。前者会删掉临时文件重新下载，后者直接换下一个来源。目录里已有、但明显偏小的文件，会被改名为 `.bad` 后重新下载。
- **返回的是 text/html 等网页内容 / HTTP 401、403**：仓库需要登录、同意协议，或者被限流。设置环境变量 `HF_TOKEN` 或 `MODELSCOPE_TOKEN` 后重跑。
- **404**：该来源没有这个文件，脚本会直接换下一个来源。所有来源都失败时，脚本最后会列出失败的文件，可以手动下载后放到 `ComfyUI/models/<目录>/`。

### 3.3 手动用 `hf` 命令下载时的注意事项

- huggingface_hub 2.x 只有 `hf` 命令，没有 `huggingface-cli`。
- `HF_HUB_ENABLE_HF_TRANSFER` 已废弃。要加速用 `HF_XET_HIGH_PERFORMANCE=1`；走镜像出问题时，可以用 `HF_HUB_DISABLE_XET=1` 退回普通 HTTP。hf-mirror 对 Xet 存储的支持情况未确认。
- 仓库里是 `split_files/...` 结构的（Wan、Qwen 的 repackaged 系列），下载后要把文件从 `split_files` 目录挪到 `models/<目录>/` 下。

## 4. 开了系统代理（Clash 等）

### 4.1 浏览器能打开 ComfyUI，但 aidrama 或脚本连不上（502、超时）

- **原因**：设置了 `HTTP(S)_PROXY` 或系统代理后，Python requests 默认把 `127.0.0.1` 的请求也发给代理。
- **已有处理**：aidrama 访问本机地址（localhost、127.x、192.168.x.x 等私有地址、`.local` 主机名）时会自动绕过代理（`aidrama/net.py`）。Linux 启动脚本会设置 `NO_PROXY=127.0.0.1,localhost`；Windows 启动脚本的健康检查也不走代理。
- **仍然失败时**：
  - ComfyUI 在另一台机器上，并且用公网 IP 或普通域名访问：把该地址加进 `NO_PROXY`。
  - 自己写的脚本或 curl：加 `--noproxy '*'`。
  - 用 aidrama 自带的工具测试连通性（用仓库 `.venv` 里的 Python 运行），可以排除代理的干扰：

```bash
python -c "from aidrama import net; print(net.get('http://127.0.0.1:8188/system_stats', timeout=5).status_code)"
```

### 4.2 开着代理后，国内镜像反而很慢；`ollama pull`、git 不走代理

- 用规则模式（国内直连），不要用全局模式，否则 hf-mirror、ModelScope、清华源都会绕到境外。
- git：`git config --global http.proxy http://127.0.0.1:7890`（端口按你的代理软件改）。
- Ollama 服务进程读的是它自己启动时的 `HTTPS_PROXY` 环境变量。改完环境变量要重启 Ollama 才生效。

## 5. ComfyUI 显存不足、速度慢、崩溃

### 5.1 显存不足（`CUDA out of memory` / `OutOfMemoryError`）

- **先看是谁占着显存**：执行 `nvidia-smi`。常见情况是 Ollama 的模型、IndexTTS、Qwen 音频模型，或者剪映、达芬奇、游戏还在显存里。
- **原因与解决**：
  - 关了显存轮转。确认配置里 `gpu.handoff: true`、`comfy.free_between_stages: true`（都是默认值）。流水线会在阶段切换前对 ComfyUI 调 `/free`、对音频服务调 `/unload`、对 Ollama 发 `keep_alive=0`。
  - LLM 不是 Ollama，或者 Ollama 不在 11434 端口，就不会被自动卸载（见 9.4）。
  - 用了 `--highvram`、`--gpu-only`、`--novram` 或 `--cpu`。这些参数会直接关闭 dynamic VRAM，H3 很容易 OOM，必须去掉。`--lowvram` 在开着 dynamic VRAM 时不起作用。
  - 同时开着剪辑软件：加 `--vram-headroom 2`（到 4），让 ComfyUI 多留出空闲显存，其他程序占用的显存也会算进去。
  - 段太长：帧数越多，latent 和中间激活越大，显存占用越高（耗时上，注意力开销近似随长度平方增长）。可以在 `aidrama.yaml` 里把 `video.max_segment_seconds` 从 12 调到 10，重新 `ad plan`。注意 `balanced` 和 `quality` 的分辨率相同（768×1344），换成 `balanced` 不会降低峰值显存；只有 `draft`（512×896）分辨率更低，但它只用于预演。
- 手动让各服务释放显存（用仓库 `.venv` 里的 Python 运行，不受代理影响）：

```bash
python -c "from aidrama import net; net.post('http://127.0.0.1:8188/free', json={'unload_models': True, 'free_memory': True}); [net.post(u + '/unload', json={}) for u in ('http://127.0.0.1:9001', 'http://127.0.0.1:9002')]"
ollama stop aidrama-llm
```

  注意：ComfyUI 的 `/free` 要等当前任务跑完才执行。

### 5.2 速度比预期慢很多，或者越跑越慢

- **参照值**：5090 上 H3 int8、1152×896、约 5 秒、20 步、pytorch 注意力，权重已在内存时约 288 秒；lightx2v Turbo 4 步约 71 秒（ComfyUI PR #15908）。README 估算 `quality` 预设下，8–10 秒的段每条约 8–15 分钟。每次切换模型后的第一条要从硬盘加载权重，会更慢。
- **原因与解决**：
  - **fast-disk**：128GB 内存的机器上，fast-disk 会跳过内存锁页，每一步都重新读 SSD。#16415（5090 + 192GB）从 36 s/it 退化到 50–90 s/it。启动脚本默认加了 `--disable-fast-disk`；如果你用 ComfyUI Desktop、Portable 或自己的命令启动，要自己加上。
  - **Windows 锁页内存上限**：ComfyUI 源码里，Windows 的锁页内存上限是物理内存的 40%（128GB 约 51GB），Linux 约 112GB。H3 一套（DiT 19.5GB + 文本编码器 14.6GB + VAE）放得下，但再叠图像模型或超分模型就会反复从硬盘重读。可以按阶段分批跑（流水线默认就这么做），或者换 Linux。WSL2 也能用，但要在 `.wslconfig` 里写 `memory=112GB`，模型不要放在 `/mnt/c`。
  - **长时间运行后内存增长**（#15759）：每跑完一集重启一次 ComfyUI（经验做法）。Linux：`bash install/linux/stop_all.sh && bash install/linux/start_all.sh`。
  - **更新 ComfyUI 后显存或内存暴涨**（#16140、#16150、#16705）：生产环境锁定 tag（默认 `v0.38.2`），不要追 master。

### 5.3 Windows：VAE 解码阶段异常慢（几分钟）

- **原因**：Windows 默认只给系统预留几百 MB 显存。#14157 中，5090 的 VAE 解码从约 10 秒恶化到 150–300 秒，多预留 4GB 后恢复。
- **解决**：把 `--reserve-vram` 从 1.5 调到 3–4：

```powershell
powershell -ExecutionPolicy Bypass -File install\windows\start_all.ps1 -Only comfy -ComfyArgs "--listen 127.0.0.1 --port 8188 --disable-fast-disk --reserve-vram 4"
```

  Linux 一般不需要；带桌面的 Linux 也遇到同样问题时：`COMFY_ARGS="--listen 127.0.0.1 --port 8188 --disable-fast-disk --reserve-vram 2" bash install/linux/start_all.sh comfy`。

### 5.4 aimdo（动态显存分配器）相关报错

| 报错关键字 | 出处 | 处理 |
|---|---|---|
| `aimdo memory compile error: could not start recording` | #16342（5090 + Win11） | 启动参数加 `--disable-comfy-compiler` |
| `HostBuffer.read_file_slice failed` | #15255、#14250 | 加 `--disable-pinned-memory`，或升级 comfy-aimdo |
| Windows 启动即崩溃，日志有 `Hook cuMemAlloc_v2 failed` | aimdo #64，装了 SageAttention2 | 卸载 sageattention。本流水线不需要它（H3 用 comfy-kitchen INT8 注意力） |

调研笔记记录 `--disable-dynamic-vram` 也能绕过 aimdo #64 的启动崩溃，但官方说这个参数将被移除，只在最后排障时用；它对另外两条报错是否有效未确认。

### 5.5 “GPU is lost”、黑屏、驱动重置

- **现象**：跑到一半屏幕闪黑，ComfyUI 报 GPU lost，或第二次运行明显变慢后驱动崩溃（#15480、#15488）。
- **解决（经验做法，未确认）**：给显卡设功耗上限，例如 `nvidia-smi -pl 500`（需管理员权限）；检查电源和 12V-2x6 供电线是否插紧；换 Linux。#15488（5070 Ti + 64GB）在 Windows 上用 bcdedit 限制系统只用 32GB 内存后，连跑 29 次没再崩，原因不明。

### 5.6 ComfyUI 网页显示异常

- 新版前端要求 Chrome ≥ 143。流水线本身不依赖网页，网页只用来看队列、预览和手动调试。

## 6. INT8 注意力报错

- **现象**：视频阶段日志出现 `! INT8 注意力报错，改用 pytorch attention 重试`，或 ComfyUI 报带 `alignment` 的错误（例如 #15494 的 `4-element alignment`）。
- **原因**：默认配置 `video.attention: comfy kitchen attention` 会在 H3 前面插入 `ModelAttentionBackend` 节点，启用 comfy-kitchen 的 INT8 注意力。社区数据不一致：有实测（5090，Turbo 8 步）称加上它采样约快 2 倍、ArcFace 和口型相关度不变；也有报告（#15494）说 ck INT8 注意力会报 `4-element alignment` 错误。
- **已有处理**：报错信息里含 `kitchen` 或 `must be aligned`（不区分大小写），并且不是显存不足（`out of memory`）时，流水线会去掉这个节点，自动重试一次；`draft` 预设的 FastH3 段不做这个重试。注意：重试时只是不再插入该节点，用的是 ComfyUI 对 H3 的默认注意力；调研笔记记录 v0.38 的 H3 模型文件已经逐 block 声明了 INT8 注意力，所以重试是否真的走 PyTorch 注意力未确认。
- **长期规避**：在工程的 `aidrama.yaml` 里固定使用 PyTorch 注意力（会慢一些）：

```yaml
video:
  attention: pytorch attention
```

## 7. 模型或节点缺失

### 7.1 `doctor` 显示“模型组 core 缺 N 个”

- **解决**：按 doctor 打印的命令补齐：`python scripts/download_models.py --comfy <ComfyUI 目录> --groups core[,fast,…] [--source modelscope]`。
- `core` 必须齐全。`fast` 用于 `balanced`/`draft` 预设；`lipsync`、`animate` 是兜底方案；`qwen21` 是非商用许可的可选组。
- 文件已经下了但仍显示缺失：检查是否放错了目录（例如多了一层 `split_files`），或者文件名和 `configs/models.yaml` 不一致。改完重启 ComfyUI 再跑 doctor。

### 7.2 `doctor` 显示“缺少节点”或版本低于 0.38

- **原因**：ComfyUI 版本太旧，缺少必需的原生节点（例如 `MiniMaxH3AddGuide` 从 v0.34 起才有，SeedVR2 原生节点从 v0.28 起）。流水线按 0.38 的节点快照编写和校验，所以 doctor 要求 ≥ 0.38。也可能是某个自定义节点和核心版本不匹配，导致整块节点没注册（discussion #15204）。
- **解决**：`cd <stack>/ComfyUI && git fetch --tags && git checkout v0.38.2`，再用 ComfyUI 的 Python 重装 `requirements.txt`。本流水线只用原生节点；排查时可以先把 `custom_nodes` 里的东西挪走。升级后用 `scripts/comfy_validate.py` 校验工作流（见 [02-安装部署](02-安装部署.md) 第 9 节）。

### 7.3 视频或图像阶段报 `node_errors` / `Value not in list`

- **原因**：工作流引用的模型文件名在 ComfyUI 的模型列表里不存在。
- **解决**：报错里会给出节点和文件名，对照 7.1 补文件。每次提交的完整工作流保存在 `<工程>/graphs/<名字>.json`，可以拖进 ComfyUI 里复现。

## 8. 音频服务（9001 IndexTTS / 9002 Qwen）

### 8.1 `doctor` 显示音频服务“未启动”

- **排查**：Linux 看 `<stack>/logs/indextts.log` 和 `qwen_audio.log`；Windows 看各自弹出的窗口。窗口一闪而过时，在 PowerShell 里手动运行 `start_all.ps1` 里对应的那条命令，就能看到报错。
- **端口被占用**：先运行 `stop_all`。还不行，就找出占用 9001/9002 的进程（Linux `ss -ltnp | grep 900`，Windows `netstat -ano | findstr 900`）。
- 音频服务默认只监听 127.0.0.1（启动脚本没有改 `--host`），并且通过本机文件路径传音频，所以必须和 aidrama 跑在同一台机器上。

### 8.2 第一次配音很慢，或第一次启动时卡在下载

- **原因**：音频服务在收到第一个请求时才加载模型（约 10–30 秒）。IndexTTS-2.5 加载时如果 `index-tts/checkpoints/hf_cache/` 里缺少辅助模型（w2v-bert-2.0、campplus、bigvgan），会先下载到这个目录。
- **解决**：启动脚本发现 huggingface.co 不通时，会自动设置 `HF_ENDPOINT=https://hf-mirror.com`。IndexTTS 自己也会测网络：huggingface.co 不通（或比 modelscope.cn 慢）时改从 ModelScope 下载，ModelScope 失败再退到 hf-mirror；可以用环境变量 `USE_MODELSCOPE=true` 强制走 ModelScope（来自 IndexTTS 源码 `indextts/utils/network_detection.py`）。想在启动时就加载模型，可以给 `audio_server.py` 加 `--preload`。

### 8.3 Qwen 音频服务报 transformers 相关的导入错误或属性错误

- **原因**：`qwen-asr` 固定依赖 `transformers==4.57.6`，`qwen-tts` 固定依赖 `4.57.3`。安装脚本装的是前者的版本，qwen-tts 用 `--no-deps` 跳过依赖检查。IndexTTS 环境固定 `transformers==4.52.1`，ComfyUI 有自己的环境。这几个环境不能混用。
- **解决**：不要往 IndexTTS 或 ComfyUI 的环境里装 qwen-tts/qwen-asr。如果 Qwen 环境确实冲突，就拆成两个环境：一个用 `--engines voicedesign` 跑在 9002，另一个用 `--engines asr` 跑在 9003，再在 `aidrama.yaml` 里写 `audio.asr_url: http://127.0.0.1:9003`（见 [02-安装部署](02-安装部署.md) 第 4 节）。

### 8.4 识别/对齐服务报 `nagisa` 或 `dynet` 相关错误

- **原因**：`qwen-asr` 0.0.6 硬依赖 `nagisa==0.2.11`（日语分词，依赖 DyNet38）。强制对齐器的模块一加载就 import nagisa，而 `qwen_asr` 包的 `__init__` 会导入对齐器，所以只用 ASR、只处理中文也需要它。PyPI 上这两个包都有 Windows/Linux 的 cp311 预编译 wheel；如果镜像缺 wheel，uv 会尝试从源码编译，没有 C++ 编译环境就会失败。具体报错文字未确认。
- **解决**：保持 Qwen 音频环境用 Python 3.11（安装脚本就是这么建的），从官方 PyPI 单独装：

```bash
uv pip install --python <stack>/qwen-audio/.venv/bin/python "nagisa==0.2.11" dynet38 --index-url https://pypi.org/simple
# Windows：--python <stack>\qwen-audio\.venv\Scripts\python.exe
```

### 8.5 配音时 OOM，或配音和 ComfyUI 同时跑时很慢

- **原因**：音频模型加载在 `cuda:0`，和 ComfyUI 共用 5090。流水线会在阶段切换时自动轮转显存；手动在 ComfyUI 网页里跑任务的同时让流水线配音，就会抢显存。
- **解决**：不要同时操作。需要时用 5.1 的命令释放显存。`GET /health` 返回的 `loaded` 字段可以看出哪些引擎正占着显存。

## 9. 本地 LLM（Ollama）

### 9.1 `doctor` 显示“模型 aidrama-llm 不存在”

- **原因**：安装脚本依次尝试拉取 Qwen3.8-27B GGUF（HF、ModelScope）、Qwen3.6-27B、Qwen3.5-27B，都失败时就不会创建别名。
- **解决**：`ollama pull <任意中文能力强的模型>`，然后 `ollama cp <模型名> aidrama-llm`。也可以直接在 `aidrama.yaml` 里把 `llm.model` 改成已有的模型名。doctor 会列出接口上已有的模型。

### 9.2 报“LLM 输出 3 次都不是合法 JSON”或“JSON 不完整”

- **原因**：`json_call` 会把解析或校验错误反馈给模型再试，总共最多调用 3 次。常见原因：模型太小；`max_tokens` 不够，输出被截断（报“JSON 不完整（可能被截断…）”）；Ollama 的上下文窗口太小，长输入被截掉（是否静默截断未确认）。
- **解决**：
  - 在 `aidrama.yaml` 里调大 `llm.max_tokens`（默认 16384），慢的话再调大 `llm.timeout`（默认 600 秒）。
  - Ollama 的上下文长度：给 Ollama 服务设置环境变量 `OLLAMA_CONTEXT_LENGTH=32768` 后重启（本仓库没有用到这个变量，未在本机验证）。当前版本的默认值是多少未确认。
  - 剧本和分镜对模型能力要求最高。效果不好时可以改用云端模型（[02-安装部署](02-安装部署.md) 第 6 节），一整部剧的 token 成本相对视频生成可以忽略。

### 9.3 思考型模型（thinking）回复为空或很慢

- **原因**：aidrama 会删掉回复里的 `<think>…</think>`（回复里只有结尾的 `</think>` 时，删掉它之前的全部内容），并且只读取接口返回的 `content` 字段。如果思考过程把 `max_tokens` 用完，正文里就没有完整 JSON，一般会报“回复中没有 JSON”或“JSON 不完整”。有的后端把思考内容放在单独的字段里，这种情况下表现是否相同未确认。
- **解决**：调大 `llm.max_tokens`；或者通过 `llm.extra` 透传降低思考强度的参数，例如 `extra: {reasoning_effort: low}`（Ollama 等后端是否支持这个参数未确认）；或者换非思考版本，再用 `ollama cp` 指到 `aidrama-llm`。

### 9.4 生成视频时 LLM 仍占着显存

- **原因**：流水线只对 Ollama 发 `keep_alive=0` 卸载模型。默认 `llm.unload: auto` 时，只有 `base_url` 里含 `:11434` 才会卸载；设成 `ollama` 时总是发卸载请求；设成 `none` 时不卸载。LM Studio、llama.cpp `llama-server`、vLLM 都不会被卸载。
- **解决**：Ollama 跑在其他端口时，设 `llm.unload: ollama`。其他后端请放到 CPU 上跑，或者在执行 `ad video` 前手动关掉。用 `ollama ps` 查看当前加载的模型。Windows 安装脚本还设了用户环境变量 `OLLAMA_KEEP_ALIVE=2m`，重启 Ollama 后生效。

### 9.5 LLM 扩写的 H3 提示词不合格

- 扩写结果违反格式规则时，流水线会回退到确定性草稿，并在日志里用 `!` 打印原因。扩写总是失败时：先跑 `ad fetch-guides`；换更大的模型；或者设 `video.refine_prompt_with_llm: false`。详见 [04-提示词指南](04-提示词指南.md) 第 4.4 节和第 7 节。

## 10. ffmpeg、字幕与字体

### 10.1 `doctor` 显示 ffmpeg / ffprobe 不在 PATH

- Windows：安装脚本用 winget 装 `Gyan.FFmpeg`，装完重开终端。Linux：`sudo apt install ffmpeg`。

### 10.2 字幕或右上角 AI 标识显示成方块，或字体不对

- **原因**：字幕样式里写的字体是 `Source Han Sans SC`，合成时用 `post.fonts_dir` 指定的目录（没设时用仓库的 `fonts/`）去找字体文件。安装脚本从 GitHub 下载思源黑体，下载失败时 `fonts/` 是空的。AI 标识用 drawtext 绘制，字体按顺序找：`fonts/` → 微软雅黑/黑体 → Noto CJK → 文泉驿 → 苹方；一个都找不到就用 ffmpeg 默认字体，中文会显示成方块。
- **解决**：把 `SourceHanSansSC-Bold.otf`（和 `-Medium.otf`）放进仓库 `fonts/`。下载地址就是安装脚本里那个：`https://github.com/adobe-fonts/source-han-sans/releases/download/2.004R/SourceHanSansSC.zip`。或者改用系统字体，例如 Linux 先 `sudo apt install fonts-noto-cjk`，再在 `aidrama.yaml` 里写：

```yaml
post:
  subtitle_font: Noto Sans CJK SC
  fonts_dir: /usr/share/fonts/opentype/noto
```

  然后重跑 `ad assemble <工程> ep01`。

### 10.3 合成时报 `No such filter: 'subtitles'` 或 `'drawtext'`

- **原因**：ffmpeg 编译时没带 libass 或 libfreetype。
- **解决**：换带这两个库的完整版 ffmpeg。检查：`ffmpeg -hide_banner -filters`，输出里要能找到 `subtitles` 和 `drawtext`。

### 10.4 怎么确认成片里的标识和响度

- 隐式标识（GB 45438-2025 附录 E 的 `AIGC` 元数据字段）：`ffprobe -v error -show_entries format_tags -of json <工程>/episodes/ep01/out/ep01.mp4`，`tags` 里要有 `AIGC` 键（`--mock` 跑出的成片已验证能看到）。
- 合成结束时日志会打印成片的 LUFS，目标是 -14。字幕位置（底边距 520px，避开平台按钮）、标识大小等合规要求见 [07-合规与授权](07-合规与授权.md)。

## 11. H3 画面与声音质量

先看 `episodes/<集>/review.html`，确认问题出在哪一层：关键帧、提示词，还是生成本身。更完整的返工决策表见 [05-质检与返工](05-质检与返工.md) 第 4 节。

### 11.1 出现剧本外的台词，台词被唱出来，或台词内容跑进画面

- **原因**：H3 自己生成音频，社区反馈它偶尔会冒出随机台词（见 [research/02-开源视频模型](research/02-开源视频模型.md)）。MiniMax-H3 的已知 issue 还有：#81 台词内容跑进画面，#68 台词被唱出来，#80 普通话转粤语失败。
- **解决**：
  1. 补抽：`ad video projects/myshow ep01 --only ep01_g03 --takes 4`。有对白的段会经过 ASR 质检，字错率超过 `audio.max_cer`（默认 15%）的条会判为不合格，自动选优时优先选字错率最低的合格条。
  2. 打开 `<工程>/episodes/ep01/prompts/ep01_g03.txt`，检查每句 `<d>[Chinese] …</d>` 是否与剧本逐字一致，有没有被扩写出额外的说话动作。可以临时设 `video.refine_prompt_with_llm: false`，用确定性草稿对比。
  3. 删掉动作描述里暗示说话的词（低语、喃喃、自言自语、嘴唇翕动等）。用 `.manual.txt` 写明除列出的台词外没有任何人说话，然后 `--force` 重抽。
  4. **ASR 质检只覆盖一部分时间**：它只回读本段第一句台词开始前 0.2 秒到最后一句结束后 0.4 秒这一段音频。没有台词的段，以及这段时间之外多出的人声，都不会被检查，只能靠人工审片发现。
  5. 仍然不过：改走 InfiniteTalk 兜底，音频就是 TTS 原声（[03-工作流SOP](03-工作流SOP.md) 第 11 节）。

### 11.2 不说话的人也在动嘴

- **原因**：H3 倾向于把口型放到画面里最显眼的正脸上。社区小样本测试（zen 技能库）：不说话的人出画或背对镜头时 12/12 正确；同框正脸时，不写闭嘴约束容易落错，写了约束后 3 次全对。不加约束时的错误率，两份调研笔记记录不一致（[research/05](research/05-对白口型与数字人.md) 记为 3 次错 2 次，[research/10](research/10-剧本分镜与自动化框架.md) 记为 3 次对 2 次），未确认。
- **解决**：
  - 确认听者已经列进该镜头的 `characters`。编译器只会给列出的非说话人加 “does not speak; the lips remain completely closed”。
  - 改构图：听者背对镜头、过肩只露轮廓，或者出画。让说话人离镜头更近、在焦点上。
  - 还不行：把听者的反应镜头单独成段，然后重新 `ad plan`。规划器只会把“前一镜 `transition` 为 `cut`、且 `method` 都是 `auto`”的相邻镜头并成一段，所以可以把它前一镜和它自己的 `transition` 改成 `fade`/`dissolve`/`flash`（成片里会变成对应的转场），或者给它设一个非 `auto` 的 `method`（`flf2v`/`t2v`/`continue`/`animate`，生成方式也会跟着变）。单镜头、无对白、`method: auto` 的段会走 FL2VA I2V，不带对白音轨。

### 11.3 脸、发型或服装漂移

- **先查关键帧**：看 `keyframes/` 里这个镜头像不像。不像就先重做关键帧，再重抽：`ad keyframes projects/myshow ep01 --only <镜头id> --force`。重做关键帧约 1 分钟一张（估算），比重抽视频便宜得多。
- **增强参考**：在 `aidrama.yaml` 里设 `video.ref_image_size: max`（锁脸更强，但更慢）。身份要求高的段不要用 `draft`：它的 Ref2VA 段用 4 步 Turbo LoRA，调研笔记记录 4 步时参考几乎不起作用。
- **减少干扰**：一段里角色越多、镜头越多，参考注意力越分散。可以设 `video.max_cuts_per_segment: 3`，或让该段只保留 2 个角色。另外，本地 ComfyUI 下 Ref2VA 的参考保真度下降是已知问题（H3 #84），多抽几条。
- **服装**：同一角色的 `outfits` 键和描述要统一，`keyframe_prompt` 里不要再写别的衣服（见 [04-提示词指南](04-提示词指南.md) 第 7 节）。

### 11.4 中远景人脸发软、五官糊

- **原因**：H3 本地只能出 768p 级画面（9:16 画布 768×1344），VAE 本身也会让皮肤细节变软。这是模型上限，不是参数问题。
- **解决**：
  - 分镜阶段让开口的镜头用中近景或特写，中远景不承担脸部表演。
  - 成片前统一用 SeedVR2 7B 超分到 1080×1920（默认开启）。超分后脸部过锐、发假时要知道：SeedVR2 官方承认对 720p 级 AIGC 素材会过锐；调研笔记的经验判断是 7B 比 3B 更忠实（没有严格评测），所以换 `upscale.model: 3b` 不一定改善，只能自己对比。
  - 少数关键镜头，可以付费用 ComfyUI 合作节点的 H3 Regenerate-2K，或其他商用 API 重做，再用 `ad add-take` 登记（[03-工作流SOP](03-工作流SOP.md) 第 11 节）。

### 11.5 对白有杂音、金属声、发音含糊

- **原因**：调研笔记记录 Turbo / 4 步 LoRA 会持续降低音频质量。按当前代码（`aidrama/config.py`）：`quality` 不用 LoRA；`balanced` 的 Ref2VA 段（有对白的段都走 Ref2VA）也不用 LoRA，只把步数降到 16 步，FL2VA 段用 lightx2v 的 8 步 Turbo LoRA；`draft` 的 Ref2VA 段用 4 步 LoRA 跑 4 步，对白音质会受损，只能用来预演。Ref2VA 没有 8 步 LoRA（调研时只找到 4 步版）。另一个可能是音频 VAE 用错了：社区汇总说音频 VAE 必须保持 fp32（本流水线用 `minimax_h3_audio_vae_fp32.safetensors`），否则音画会不同步。
- **解决**：
  - 对白段用 `quality` 预设补抽，旧的条会保留：`ad video projects/myshow ep01 --only ep01_g03 --preset quality --takes 4`。
  - 合成时用的是所选条目自带的音频（超分会原样带上这条音轨）。画面满意、只有声音坏了时，可以手动把对白换成 TTS 原轨，再登记回来。这样会丢掉 H3 生成的环境声；该做法在真实输出上未验证。条目的实际文件名（带内容签名，例如 `ep01_g03_<签名>_t2.mp4`）以 `project.yaml` 或 review.html 里记录的路径为准：

```bash
# 在仓库根目录执行；<条目文件> 换成 project.yaml 里这一条的 path
ffmpeg -i projects/myshow/<条目文件> -i projects/myshow/episodes/ep01/audio/ep01_g03_dialogue.wav -map 0:v -map 1:a -c:v copy -c:a aac -shortest ep01_g03_tts.mp4
ad add-take projects/myshow ep01 ep01_g03 ep01_g03_tts.mp4
```

  - 口型和配音整体错位：先检查配音时长和语速，长句拆成两句；也可以试实验选项 `video.anchor_dialogue_audio: true`（用 AddGuide 把对白音轨钉在第 0 帧，效果未验证）；反复不过就走 InfiniteTalk。

### 11.6 切镜时间不对，或该切的地方没切

- **现象**：质检报“切镜缺失或偏移：计划在 X 秒切镜，未检测到”（硬伤），或“提示：检测到计划外的画面突变”（只提示）。允许误差是 0.35 秒。
- **原因**：一段里从第 2 镜开始，每个切点都用 `MiniMaxH3AddGuide` 把该镜头的关键帧钉在 `frame_idx=round(t×24)`（第 1 镜的关键帧只作为参考图）。段太长、镜头太多时，模型可能切晚或漏切。相邻两镜的关键帧景别和机位太像时，即使真的切了，场景检测也可能测不出来（误报）。
- **解决**：
  1. 先在 review.html 里看实际有没有切。是误报的话，直接 `ad pick` 选这一条。
  2. 补抽几条。
  3. 让相邻镜头的景别或机位差别明显（例如中景接特写），重做关键帧。
  4. 减少每段的镜头数：`aidrama.yaml` 里设 `video.max_cuts_per_segment: 3`（或 `max_segment_seconds: 10`），重新 `ad plan`，再 `ad video <工程> ep01`（内容变了的段没有可沿用的旧条，会自动重新生成；只想丢掉某段的旧条重抽时，加 `--only <段> --force`）。重新规划后段号可能变化：内容没变、只是段号变了的段，`plan` 会自动把 `.manual.txt` 改到新段号；段号没变但镜头变了的，旧的 `.manual.txt` 会被改名为 `*.orphan.txt`，需要自己检查后重新放置。
  5. 手改提示词时不要动 `[Shot N] At MM:SS.mmm` 的时间戳。校验器会检查切点是否递增、是否小于本段时长；但改了文本里的时间戳，AddGuide 锚点不会跟着动。

### 11.7 高速动作碎、糊（打斗、奔跑）

- **原因**：H3 已知问题（#74）。
- **解决**：镜头设 `method: animate`，用真人表演驱动 Wan Animate 2（[03-工作流SOP](03-工作流SOP.md) 第 11 节）；或者把动作拆成幅度更小的几个镜头。

### 11.8 续写镜头（`method: continue`）被跳过，或衔接处跳帧

- **现象**：日志显示 “… 是续写镜头，但上一段还没有视频，跳过”。
- **原因**：续写段的首帧取自上一段所选条目在成片里用到的最后一帧（按规划时长取，不是文件的最后一帧），所以上一段必须先生成。生成续写段时，上一段当前选中的条会被锁定（等同人工 pick，日志会打印“锁定 take N”），之后补抽不再自动改选。
- **解决**：先生成上一段，再生成这一段。如果之后用 `ad pick` 改了上一段的选条，要对续写段重新生成：`ad video <工程> ep01 --only <续写段> --force`，否则衔接处对不上。
